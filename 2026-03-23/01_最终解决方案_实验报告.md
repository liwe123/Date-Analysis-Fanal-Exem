# 实验04 最终解决方案（代码/答案）

## 一、实验任务

使用实证证据比较 CSV、JSON、Parquet 三种格式在以下方面的表现：
- 存储大小
- 读取速度
- 类型安全性

并验证题目要求的关键指标：

`1 - (Parquet大小 / JSON大小)`

## 二、实验设置

- 数据规模：1,000,000 行
- 字段：`transaction_id`, `user_name`, `category`, `price`, `timestamp`
- `category` 为低基数列（4个类别），用于观察字典编码收益
- 运行脚本：`run_experiment.py`

## 三、实测结果

### 1) 数据规模与内存
- DataFrame 内存占用：**155.34 MB**

### 2) 三种格式体积对比
- CSV：**69.83 MB**
- JSON：**122.53 MB**
- Parquet：**23.27 MB**

### 3) 指标计算（题目指定公式）

`1 - (Parquet / JSON) = 1 - (23.27 / 122.53) = 81.01%`

结论：Parquet 相比 JSON 减少 **81.01%** 的体积。  
补充：Parquet 相比 CSV 减少 **66.68%**。

### 4) 读取速度对比（平均价格计算）
- CSV 全量读取时间：**1.0119 s**
- Parquet 按列读取（`price`）时间：**0.3254 s**
- 加速比（CSV/Parquet）：**3.11x**

平均价格一致性验证：
- CSV：`254.989886`
- Parquet：`254.989886`

说明：两者均得到同一统计结果，证明格式变更不影响业务结论正确性。

## 四、字典编码两句话解释（题目硬要求）

Parquet 会识别 `category` 这样的低基数列，并将字符串值映射为更短的整数编码（如 0/1/2/3）再写入。  
这样避免了在每一行重复存储完整字符串（例如反复写 `Electronics`），因此文件更小、读取更快。

## 五、模式防御（安全性）

坏数据示例：将 `price` 写成字符串 `"Expensive"`。  
触发异常：`could not convert string to float: 'Expensive'`

结论：类型错误可在写入/转换阶段暴露，而不是长期潜伏到报表读取阶段才爆炸。

## 六、最终结论

在本次实验环境中，Parquet 在**体积压缩**与**读取性能**上均优于 CSV/JSON，且在类型约束上更利于数据质量控制。  
对于分析型与大数据场景，应优先选用 Parquet 作为主存储格式。
