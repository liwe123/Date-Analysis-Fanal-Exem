# 高级工程师评审（元反思）

## 1. 问题表述与提示策略（对应 30%）

本次任务不是单纯“做出实验结果”，而是一个双约束问题：  
一方面要满足《实验04 – 压缩战争》的技术要求（数据规模、性能对比、公式计算、类型防御、Notebook交付）；另一方面要满足《更新_AI集成作业与批判框架》的提交结构（最终方案 + AI 对话记录 + 元反思），并可被老师按 30/50/20 权重评分。

因此我采用了分层提示策略，而不是“让 AI 一次性全部完成”：
- 第一步：先只做信息抽取，明确两份 PDF 的硬要求，不急着写代码。
- 第二步：拿到明确约束后，再执行实验脚本并收集实测证据，避免凭示例值“编结果”。
- 第三步：最后才组织提交格式，确保三份材料齐全，且互相一致（数据结果在 notebook、summary、评审文档中一致）。

这种分解能降低风险：如果先写答案再回头核对要求，容易出现“结果对但格式不对”的失分。

## 2. 对 AI 的批判（对应 50%，核心）

### 2.1 早期失败点

AI 在最开始对 PDF 抽取的判断并不稳定，主要有三类问题：
- 环境假设错误：默认系统里已有 PDF 解析库，实际没有，导致首次读取失败。
- 文件名匹配脆弱：中文路径和长破折号导致脚本无法稳定命中文件。
- 误判乱码来源：初看像“文本损坏”，实际上核心问题是终端编码展示，而非源文本不可用。

这些问题如果不被识别，后续会出现两类严重后果：
- 一是直接跳过 PDF 细则，凭经验做实验，容易漏掉“公式写法”“两句话解释”等硬性条款；
- 二是提交虽然能运行，但无法被新评分框架认可（缺 AI 过程记录与元反思）。

### 2.2 AI 结果中的潜在误导

题目样例中提到“Parquet 可能 ~30x 提速、~90% 压缩”，但本机实测只有 3.11x 读取提速、81.01% 相对 JSON 压缩。  
如果盲信样例值并照抄，会产生“实验报告与实际数据不一致”的诚信问题。  
因此必须坚持实测优先：报告写本次环境的真实数值，并解释为什么与示例存在差异（硬件、I/O、数据分布、缓存策略等）。

### 2.3 代码层面的可疑点审计

我重点审计了以下细节，防止“看起来能跑、实则不严谨”：
- 读取比较是否公平：CSV 读取全表，Parquet 读取 `price` 列，这是题目预期场景（列剪枝），并在文档中显式说明。
- 指标公式是否严格按题目：使用 `1 - (Parquet/JSON)`，未替换为其他近似表达。
- 坏数据实验是否可复现：固定触发 `price='Expensive'` 的类型转换异常，并记录原始错误信息。

## 3. 迭代与修正（对应 50% 的“迭代能力”）

为修正上述问题，采取了以下迭代动作：
- 从“直接读 PDF”改为“先提取 TXT，再以 UTF-8 输出校验”；
- 从“字符串匹配中文文件名”改为“Unicode 转义匹配”，提高路径稳定性；
- 从“手写结论”改为“先运行脚本生成 `metrics.json`，再让 notebook/文档读取同一数据源”，避免多处数字不一致；
- 从“单文件提交”改为“三件套提交”，严格对应新框架要求。

迭代后的结果是：  
不仅完成了实验代码，还形成了可追溯证据链（脚本 -> 指标文件 -> Notebook -> 报告），降低了“结果正确但过程不可审计”的风险。

## 4. 最终有效性（对应 20%）

最终提交满足以下约束：
