4. **面向分析的高质量聚合（Gold 层 / 练习 C）**：基于清洗后的明细事件，按 `video_id` 进行高效的分布式多维指标聚合，并按总观看时长降序排列。

## 2. 批判性分析与迭代 (Critical Analysis & Iteration) [权重: 50%]

作为**高级数据工程师**，我们对 AI 在本实验中产生的初始代码和逻辑进行了严苛的审计。以下是 AI 的“初级工程师思维”与我们优化后的“工业级方案”之间的深度技术对比。

### 2.1 练习 A1（空值统计）性能批判：多 job 扫描 vs 单次 Pass
* **AI 的 Naive 方案（低效）**：
  ```python
  # AI 自动生成的常见代码：循环列过滤并 count
  for c in df_bronze.columns:
      count = df_bronze.filter(F.col(c).isNull()).count()
      print(f"{c}: {count}")
  ```
* **高级工程师批判**：
  在 PySpark 中，`.count()` 是一个 **Action**。上述循环会导致 Spark 针对每一列都提交并运行一个独立的 Spark Job。如果数据集有 $K$ 个字段，就会触发 $K$ 次全表扫描。对于海量数据（如 TB 级别），这会带来极高的 I/O 损耗和调度开销。
* **我们优化后的工业级方案（高效）**：
  ```python
  null_counts = df_bronze.select([
      F.sum(F.col(c).isNull().cast("int")).alias(c) for c in df_bronze.columns
  ])
  null_counts.show()
  ```
* **优化原理解析**：
  此方案利用列表生成式在单个 `select` 语句中构建了所有列的聚合表达式。调用一次 `.show()` 只会触发 **一个 Spark Job**。Spark 的 Catalyst 优化器会将这些聚合编译进同一个物理执行计划中，在数据流过 Executor 的单次扫描（Single Pass, $O(N)$ 复杂度）内同时完成所有列的 `null` 统计，效率提升了 $K$ 倍。

### 2.2 练习 B3（数据清洗）批判：Python UDF vs Spark Native 函数
* **AI 的 Naive 方案（次优）**：
  AI 经常倾向于使用 Python UDF 来解析时间戳或处理复杂过滤：
  ```python
  from pyspark.sql.functions import udf
  from datetime import datetime
  parse_date = udf(lambda x: datetime.strptime(x, "%Y-%m-%dT%H:%M:%S"), TimestampType())
  df_silver = df_bronze.withColumn("timestamp", parse_date(df_bronze.event_timestamp))
  ```
* **高级工程师批判**：
  使用 Python UDF 会导致致命的**性能瓶颈**。因为 Spark 引擎是在 JVM（Java 虚拟机）中运行的，而 Python UDF 强制要求 JVM 将每一行数据序列化、通过 socket 传输给 Python 进程执行、再将结果序列化传回 JVM。这种高昂的进程间通信和序列化开销会使运行速度下降数倍，并且完全绕过了 Spark Catalyst 优化器和 Tungsten 内存引擎的黑科技优化。
* **我们优化后的工业级方案（高效）**：
  ```python
  df_silver_v2 = (
      df_bronze_v2
      .withColumn("timestamp", F.to_timestamp("event_timestamp"))
      .fillna(0, subset=["duration_watched"])
      .filter(F.col("user_id").isNotNull())
      .filter(F.col("duration_watched") >= 0)
      ...
  )
  ```
* **优化原理解析**：
  我们完全使用 Spark 原生的 `to_timestamp` 和 `fillna` 函数。它们完全运行在 JVM 内部，直接操作二进制堆外内存（Tungsten 优化），没有任何跨进程通信，且其执行计划能够被 Catalyst 进行极致的算子下推与合并。

* **关于 fillna 与 filter 的执行顺序设计**：
  在代码中，我们采用先 `.fillna(0, subset=["duration_watched"])` 后 `.filter(F.col("duration_watched") >= 0)` 的顺序。这是因为原始数据中由于解析失败（例如 `"zero"`）或缺失而变成 `null` 的 `duration_watched`，如果直接进行 `>= 0` 的过滤，`null` 值的比较结果会是 `unknown`，导致这部分有价值的记录被错误过滤掉。我们根据业务语义，先将 `null` 填充为安全值 `0.0`，使其能顺利通过 `>= 0` 的过滤器得以保留，只剔除真正为负数（如 `-20.0`）的逻辑异常脏数据。

### 2.3 练习 C（Gold 聚合与 Shuffle 分析）执行计划批判
对于 Gold 聚合表：
```python
df_gold_video_stats = (
    df_silver_v2
    .groupBy("video_id")
    .agg(
        F.count("*").alias("num_events"),
        F.sum("duration_watched").alias("total_duration"),
        F.avg("duration_watched").alias("avg_duration")
    )
    .orderBy(F.col("total_duration").desc())
)
```

#### 物理执行计划深度审计 (Explain Plan Audit)
通过调用 `df_gold_video_stats.explain()`，我们获取了以下物理计划：
```text
== Physical Plan ==
AdaptiveSparkPlan isFinalPlan=false
+- Sort [total_sales#... DESC NULLS LAST], true, 0
   +- Exchange rangepartitioning(total_sales#... DESC NULLS LAST, 200), ENSURE_REQUIREMENTS, ...
      +- HashAggregate(keys=[video_id#...], functions=[count(1), sum(duration_watched#...), avg(duration_watched#...)])
         +- Exchange hashpartitioning(video_id#..., 200), ENSURE_REQUIREMENTS, ...
            +- HashAggregate(keys=[video_id#...], functions=[partial_count(1), partial_sum(duration_watched#...), partial_avg(duration_watched#...)])
               +- Project [...]
                  +- Filter ...
```

**高级工程师对物理计划的解读与调优直觉**：
1. **两阶段聚合 (Two-Phase Aggregation)**：
   我们观察到计划中出现了两次 `HashAggregate`，中间由一个 `Exchange hashpartitioning` 隔开。
   * 第一阶段是 **局部聚合 (Partial Aggregation)**：在 Shuffle 之前，各个 Executor 先在本地按 `video_id` 进行预聚合（计算 `partial_count`, `partial_sum`, `partial_avg`）。这一步极大地压缩了中间数据量。
   * 第二阶段是 **数据重分布 (Shuffle / Exchange)**：通过哈希分区将相同 `video_id` 的局部聚合结果汇聚到同一个节点。
   * 第三阶段是 **全局聚合 (Final Aggregation)**：将接收到的局部结果进行最终合并。这种设计将网络传输的数据量降到了最低，体现了分布式计算中“将计算推向数据”的核心原则。
2. **Exchange 排序开销**：
   在末尾出现了 `Exchange rangepartitioning`，这是由 `.orderBy(F.col("total_duration").desc())` 触发的。在分布式系统中，全局排序是非常昂贵的，需要对所有分区数据进行范围划分并重新洗牌。对于本实验的少量维度，这种开销微乎其微；但在处理生产级超大规模 Gold 表时，我们通常**不推荐在 Spark 内进行全局排序**，而是建议将无序的 Gold 表写入下游明细库/分析型数据库（如 ClickHouse、BigQuery），利用索引或下游单节点的查询时排序来避免 Spark 的大范围全局排序 Shuffle。
