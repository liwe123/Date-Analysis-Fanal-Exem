\section{执行摘要}
% ─────────────────────────────────────────────────────────────

\textbf{业务问题}：企业员工每天在数百份非结构化文档中查找答案，传统关键词搜索无法理解``交作业''与``提交方式''的语义等价关系，导致重复提问率高、信息检索效率低下。

\textbf{为什么传统方法做不到}：关键词搜索依赖字面匹配——用户搜``怎么交作业''，文档中写的是``提交方式''，返回零结果。当文档规模超过数百份且表述方式多样时，基于 TF-IDF 或 BM25 的检索召回率急剧下降。

\textbf{核心交付}：我们构建了一个端到端 RAG 系统，从 176 篇杂乱文档自动构建可搜索向量索引，支持语义检索 + 元数据过滤 + LLM 答案生成 + 来源追溯。系统在 41 个域内查询上实现 87.8\% 的 Recall@3，端到端稳态延迟 6.2 秒，建库成本 $<$\textyen 1。

\section{系统架构}
% ─────────────────────────────────────────────────────────────

\subsection{数据流}

系统采用七层流水线架构，数据从原始文档流向可查询的向量索引：

\begin{verbatim}
原始文档 (176篇)
  | ingest.py (摄取)
  v
clean_text() (清洗: HTML/实体/控制符/空白)
  | chunk_text() (分块: 段落->句子->贪心->滑窗)
  | extract_metadata() (LLM 提取元数据)
  v
Qwen3-Embedding-0.6B (本地GPU嵌入, 1024维)
  | ChromaDB (HNSW索引, cosine距离)
  v
query_parser.py (LLM意图解析)
  | embed_store.search() (混合检索)
  | qa.py (答案生成 + 来源标注)
  v
CLI / Streamlit Web 界面
\end{verbatim}

\section{设计决策与取舍}
% ─────────────────────────────────────────────────────────────

\subsection{向量数据库：ChromaDB vs Milvus vs Qdrant}

\begin{table}[H]
\centering
\caption{向量数据库选型对比}
\label{tab:vectordb}
\begin{tabular}{@{}p{1.8cm}p{2.2cm}p{2.2cm}@{}}
\toprule
\textbf{方案} & \textbf{优势} & \textbf{劣势} \\
\midrule
\textbf{ChromaDB} & pip install 即用，零部署 & 不支持分布式，复合语法不直观 \\
Milvus & 生产级分布式 & 需 Docker+etcd+MinIO \\
Qdrant & Rust 高性能 & 需独立服务进程 \\
Pinecone & 全托管 & 付费 SaaS，数据外传 \\
\bottomrule
\end{tabular}
\end{table}

\textbf{选择理由}：课程场景无并发/分布式需求，ChromaDB 零部署成本。已做抽象封装，未来可平滑迁移。已知代价：复合 where 条件需显式 \$and 操作符。

\subsection{分块策略：四层语义分块}

采用\textbf{四层优先级}算法：段落边界$\to$句子边界$\to$贪心合并$\to$滑窗切割。参数：chunk\_size=700，overlap=120。

\begin{itemize}
  \item \textbf{固定长度}：实现快但破坏语义——可能把一句话切在中间
  \item \textbf{四层语义分块}：尊重边界，重叠确保连续性（\textbf{选择}）
  \item \textbf{标题感知}：依赖文档格式，不适用于 FAQ
\end{itemize}

\textbf{700 字符选择依据}：$<$400 导致语义碎片化，$>$1000 稀释向量聚焦度。700 字符约 350 中文字，平衡精度与完整性。

\subsection{LLM 选择：DeepSeek V4 Flash}

DeepSeek 与 GPT-4o-mini 同价位（$\sim$\$0.15/百万 token），国内网络访问更稳定。本地 7B 模型在 CPU 上延迟 $>$10s，不适合交互场景。

\subsection{查询解析：LLM 意图提取}

用一次轻量 LLM 调用将自然语言转为结构化参数：
\begin{verbatim}
输入: "2024年的通知讲了啥"
输出: {search_query: "通知",
       filters: {year:2024, category:"notice"}}
\end{verbatim}

\textbf{回退策略}：JSON 解析异常时，search\_query 回退为原始问题，filters=None，降级为纯语义搜索。评估中 3/50 个查询触发回退。

\subsection{失效模式}

\textbf{失效 1：复合 where 条件不兼容。} Q31 ``2025年的通知''触发 ChromaDB 报错，回退为纯语义搜索。根因：ChromaDB 不支持隐式 AND。已修复：自动转为 \$and 格式。

\textbf{失效 2：超纲查询幻觉。} Q44 ``Python for循环''检索到 SO 代码片段，LLM 给出详细代码。根因：检索结果表面相关但主题不匹配。修复方向：System Prompt 增加主题相关性约束。

\textbf{失效 3：查询解析 JSON 错误。} Q32/Q38/Q39 返回非标准 JSON。系统正确回退为纯语义搜索，但丢失过滤能力。

\subsection{事后剖析}

\textbf{失败 1：SentenceTransformer 方法名变更。} commit 92bc9b2 将 \texttt{get\_sentence\_embedding\_dimension()} 改为 \texttt{get\_embedding\_dimension()}，基于 PyTorch deprecation 警告。但当前版本仍用旧方法名，导致全链路崩溃。单元测试因 Mock 了整个模型未发现。\textbf{教训}：Mock 测试无法发现 API 兼容性问题；需集成冒烟测试。

\textbf{失败 2：极短文档静默丢弃。} 早期 \texttt{clean\_text()} 对 $<$10 字符文档直接丢弃，导致 FAQ 短答案丢失。修复：\texttt{chunk\_text()} 末尾兜底保留非空极短文档。\textbf{教训}：清洗应区分``噪声''和``短但有效''内容。
