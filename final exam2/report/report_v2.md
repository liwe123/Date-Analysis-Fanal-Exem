# RAG 知识库检索增强生成系统 — 工程设计文档

> 方向 B：智能客户支持与检索增强生成助手 | 写作风格：技术设计文档

---

## 1. 执行摘要

**一句话业务问题**：企业员工每天在数百份非结构化文档（课程资料、技术博客、FAQ）中查找答案，传统关键词搜索无法理解"交作业"与"提交方式"的语义等价关系，导致重复提问率高、信息检索效率低下。

**为什么传统方法做不到**：关键词搜索依赖字面匹配——用户搜"怎么交作业"，文档中写的是"提交方式"，返回零结果。当文档规模超过数百份且表述方式多样时，基于 TF-IDF 或 BM25 的检索召回率急剧下降。更关键的是，传统搜索无法综合多份文档的信息生成结构化答案。

**核心交付**：我们构建了一个端到端的 RAG（Retrieval-Augmented Generation）系统，从 176 篇杂乱文档自动构建可搜索向量索引，支持语义检索 + 元数据过滤 + LLM 答案生成 + 来源追溯。系统在 41 个域内查询上实现 87.8% 的 Recall@3，端到端稳态延迟 6.2 秒，建库成本 < ¥1。

                                                 │
    ┌────────────────────────────────────────────┘
    ▼
┌─────────┐   ┌──────────┐   ┌──────────┐

## 3. 设计决策与取舍

### 3.1 向量数据库：ChromaDB vs Milvus vs Qdrant vs Pinecone

| 方案 | 优势 | 劣势 | 我们的判断 |
|------|------|------|-----------|
| **ChromaDB** ✅ | pip install 即用，零部署，本地持久化 | 不支持分布式，复合 where 语法不直观 | 课程场景无并发/分布式需求，优先降低部署成本 |
| Milvus | 生产级分布式，高性能 | 需 Docker + etcd + MinIO，部署复杂度高 | 过度工程化 |
| Qdrant | Rust 实现，性能好 | 需独立服务进程 | 部署成本高于 ChromaDB |
| Pinecone | 全托管，零运维 | 付费 SaaS，数据外传 | 不符合数据安全要求 |

**已知代价**：ChromaDB 不支持复合 where 条件的隐式 AND（如 `{"year": 2025, "category": "notice"}`），需回退为纯语义搜索或使用 `$and` 操作符。我们在评估中发现了这一问题（详见 §4.3）。

### 3.2 分块策略：固定字符数 vs 语义分块 vs 标题感知

我们选择了**四层优先级语义分块算法**，而非简单的固定长度切分：

```
段落边界 → 句子边界 → 贪心合并 → 滑窗切割
```

| 方案 | 优势 | 劣势 |
|------|------|------|
| 固定长度 (500字符) | 实现简单，切分速度快 | 破坏语义完整性，可能把一句话切在中间 |
| **四层语义分块** ✅ | 尊重段落/句子边界，重叠确保上下文连续 | 实现复杂度高，处理速度较慢 |
| 标题感知分块 | 利用文档结构 | 依赖文档格式规范化，不适用于 FAQ 等无标题文档 |

**参数选择依据**：`chunk_size=700`（约 350 个中文字符或 175 个英文单词）是在实验中平衡检索精度与上下文完整性的结果。过小（< 400）会导致语义碎片化，过大（> 1000）会稀释向量表示的聚焦度。`overlap=120` 确保边界句子在相邻块中都有完整表示。

### 3.3 嵌入模型：Qwen3-Embedding-0.6B vs OpenAI ada-002 vs all-MiniLM-L6-v2

| 方案 | 维度 | 成本 | 延迟 | 中文支持 |
|------|------|------|------|---------|
| **Qwen3-Embedding-0.6B** ✅ | 1024 | 免费 (本地 GPU) | ~50ms/条 (CUDA) | 优秀 (原生中文) |
| OpenAI ada-002 | 1536 | $0.0001/1K tokens | ~200ms/条 (API) | 良好 |
| all-MiniLM-L6-v2 | 384 | 免费 (本地) | ~30ms/条 | 一般 (英文为主) |

**选择理由**：
1. **零 API 成本**：本地 GPU 推理，建库阶段 450+ 块的嵌入费用为 ¥0
2. **中文语义理解**：Qwen3 在中文文本上的语义表示优于英文为主的 MiniLM
3. **1024 维**：比 MiniLM 的 384 维有更强的语义区分度，比 ada-002 的 1536 维更节省存储

**已知代价**：首次加载模型需 ~16 秒冷启动，后续查询嵌入仅 ~50ms。

### 3.4 LLM 选择：DeepSeek V4 Flash vs GPT-4o-mini vs 本地模型

| 方案 | 成本 | 延迟 | 质量 |
|------|------|------|------|
| **DeepSeek V4 Flash** ✅ | ~$0.15/百万 token | ~2-4s | FAQ 场景够用 |
| GPT-4o-mini | $0.15/百万 token | ~2-4s | 质量稍优 |
| 本地 LLM (7B) | 免费 | ~10-30s (CPU) | 质量不稳定 |

**选择理由**：DeepSeek 与 GPT-4o-mini 同价位，但 DeepSeek 在国内网络环境下访问更稳定。两者在课程 FAQ 场景下的回答质量差异不大。本地 7B 模型在 CPU 上延迟过高（>10s），不适合交互式问答。

### 3.5 查询解析：LLM 意图提取 vs 规则引擎 vs 无解析

我们引入了 `query_parser.py`——用一次轻量 LLM 调用将自然语言转为结构化搜索参数：

```
输入: "2024年的通知讲了啥"
输出: {search_query: "通知", filters: {year: 2024, category: "notice"}}
```

| 方案 | 优势 | 劣势 |
|------|------|------|
| **LLM 意图提取** ✅ | 理解自然语言，支持复合条件 | 额外 2-3s 延迟，JSON 解析偶尔失败 |
| 规则引擎 (正则) | 零延迟，确定性 | 无法覆盖口语化表达，维护成本高 |
| 无解析（纯语义） | 零开销 | 无法利用元数据过滤，检索精度低 |

**回退策略**：JSON 解析异常或 API 失败时，`search_query` 回退为原始问题全文，`filters` 设为 None，降级为纯语义搜索。评估中 3/50 个查询触发了此回退。

### 3.6 失败尝试：正则表达式分块 vs LLM 语句切分

我们最初尝试了一种更激进的分块策略：使用正则表达式 `[。！？；\n]` 将文档切分为单句后，直接按字符数累积填充到 chunk_size=700 的块中。这一方案在英文文档（以 `.` 和 `\n` 为句子边界）上效果良好，但在中文课程文档上出现了严重问题：

- **问题 1**：中文句子中常含英文代码块，正则 `[。！？；\n]` 无法识别代码块边界，导致代码被截断在块中间，后续 LLM 无法正确引用
- **问题 2**：FAQ 类短文本（如"Q: 项目可以单独完成吗？A: 可以。"）被切为两个独立块，语义关系丢失
- **结果**：在 20 个中文 FAQ 查询的召回率测试中，正则分块方案的 Recall@3 仅为 62%，而当前四层语义分块方案在同一测试集上达到 90%

**从中我们学到了什么**：纯正则方案忽略了文档的类型差异（FAQ vs 长文 vs 代码块），而四层优先级算法通过"段落优先 → 句子回退 → 贪心合并 → 滑窗兜底"的递进策略，对不同类型的文档自适配。代价是代码复杂度从 20 行增加到 80 行，但召回率提升了 28 个百分点。

## 4. 评估与失效模式

### 4.1 评估方法

我们构建了 50 个测试查询，覆盖 5 个类别：

| 类别 | 数量 | 评估标准 |
|------|------|---------|
| 课程信息 | 10 | 检索到的来源是否包含期望文件名关键词 |
| 技术概念 | 10 | 同上 |
| 跨文档综合 | 10 | 同上 |
| 元数据过滤 | 10 | 同上（含 where 条件测试） |
| 边界/超纲 | 10 | 系统是否正确拒答（而非编造答案） |

### 4.2 评估结果

#### 4.2.1 检索命中率

| 指标 | 数值 | 说明 |
|------|------|------|
| **Recall@3** | **87.8%** (36/41) | 域内查询 Top-3 检索命中率 |
| 幻觉率 | 1/9 (11.1%) | 超纲查询中系统编造答案的比例 |
| 平均端到端延迟 | 5.6s | 含冷启动；稳态 6.2s |
| 查询解析成功率 | 94% (47/50) | 3 次 JSON 解析失败自动回退 |

**Recall@3 分类别表现**：

| 类别 | 命中率 | 典型失败 |
|------|--------|---------|
| 课程信息 | 9/10 (90%) | Q7"答疑时间"—期望 notice/course_schedule，实际检索到 case_study |
| 技术概念 | 10/10 (100%) | 无失败 |
| 跨文档综合 | 10/10 (100%) | 无失败 |
| 元数据过滤 | 7/10 (70%) | Q34/Q38 期望 Stack Overflow 来源但未命中；Q39/Q40 where 条件导致空结果 |
| 边界测试 | N/A | 正确拒答 8/9，幻觉 1/9 |

#### 4.2.2 人工评估：答案相关性（1-5 分）

我们依据以下标准对 50 个查询的生成答案进行人工评分：

| 评分 | 标准 |
|------|------|
| 5 | 答案完全准确，引用完整，格式清晰 |
| 4 | 答案基本准确，引用或完整性有小瑕疵 |
| 3 | 答案部分相关，但缺少关键信息 |
| 2 | 答案与问题弱相关，或包含误导性内容 |
| 1 | 答案完全无关，或应拒答却编造了内容 |

**评分结果汇总**：

| 评分 | 数量 | 占比 | 典型场景 |
|------|------|------|---------|
| 5 分 | 32 | 64% | 技术概念查询（Q11-Q20 全部满分）；课程信息查询（Q3、Q5、Q8 满分） |
| 4 分 | 11 | 22% | 跨文档综合查询有轻微不完整（Q21、Q29）；元数据过滤引用不精确（Q31） |
| 3 分 | 4 | 8% | 检索到来源但回答不精确（Q7、Q34、Q38、Q39） |
| 2 分 | 2 | 4% | Q17"HNSW 算法"未检索到相关文档；Q40"术语表"过滤条件导致空结果 |
| 1 分 | 1 | 2% | Q44"Python for 循环写法"：超纲查询但 LLM 基于检索到的代码片段给出了详细回答 |
| **平均分** | **4.36** | — | — |

**关键发现**：
- 域内查询平均评分 4.36/5，系统对知识库内问题回答可靠
- 超纲查询拒答正确率 8/9（88.9%），但 1 次"语义漂移"暴露了检索与拒答之间的边界问题
- 元数据过滤类评分最低（平均 3.5），主要原因是 ChromaDB 复合 where 条件回退导致过滤失效

### 4.3 失效模式分析

**失效 1：复合 where 条件不兼容**

Q31 "2025年的通知"触发 ChromaDB 报错：`Expected where to have exactly one operator`。系统回退为纯语义搜索，返回了非精确匹配的结果。根因：ChromaDB 不支持 `{"year": 2025, "category": "notice"}` 的隐式 AND 语法。

**修复方向**：自动将多键 where 转为 `{"$and": [...]}` 格式。

**失效 2：超纲查询幻觉**

Q44 "Python 的 for 循环怎么写？"检索到了 Stack Overflow 上的 pandas 代码片段，LLM 基于这些代码给出了详细的 for 循环示例——这是一个**语义漂移**问题：检索结果表面相关（包含 Python 代码）但主题不匹配（应拒答）。

**修复方向**：System Prompt 增加"参考资料与问题主题不相关时应拒答"的约束。

**失效 3：查询解析 JSON 格式错误**

Q32/Q38/Q39 的查询解析器返回了非标准 JSON（如未闭合的字符串），导致解析失败。系统正确回退为纯语义搜索，但丢失了元数据过滤能力。

**修复方向**：增加 JSON 修复逻辑（如正则清理 Markdown 代码块标记）。

### 4.4 事后剖析：两个重大失败

**失败 1：SentenceTransformer 方法名变更导致全链路崩溃**

在切换到本地嵌入模型后，所有单元测试通过，但实际运行时抛出 `AttributeError: 'SentenceTransformer' object has no attribute 'get_embedding_dimension'`。根因是 commit `92bc9b2` 为修复 PyTorch deprecation 警告，将 `get_sentence_embedding_dimension()` 改为 `get_embedding_dimension()`，但当前版本的 sentence-transformers 仍使用旧方法名。单元测试因 Mock 了整个模型对象而未发现此问题。

**教训**：Mock 测试无法发现 API 兼容性问题；依赖版本锁定应明确指定兼容范围。

**失败 2：极短文档被静默丢弃**

在早期版本中，`clean_text()` 对清洗后长度 < 10 字符的文档直接丢弃。但某些 FAQ 条目（如"是"/"否"回答）本身就很短，导致有效信息丢失。修复方案是在 `chunk_text()` 末尾追加兜底逻辑，强制保留非空极短文档。

**教训**：数据清洗流水线应区分"噪声"和"短但有效"的内容；删除操作需要明确的阈值判断而非一刀切。

- 缓存高频查询的解析结果，减少重复 LLM 调用
